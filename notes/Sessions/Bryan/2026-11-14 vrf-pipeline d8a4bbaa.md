# A MAK VR-Forces importer for the editor's models

**Asked:** "Create a pipeline that takes a .glb model generated by Blender and creates the files for importing it as
a simulation object into MAK VR-Forces, with correctness testing of the import." Later: read the VR-Forces Users
Guide with attention to part articulation; remove the Blender dependency; compare against a hand import; integrate
the importer into this editor; support any model kind (humans, ground vehicles, aircraft, animals, buildings,
munitions); name the entity after the ship project; write a technical document for engineers.

## What VR-Forces needs for one entity
Five artefacts, all now generated (layout matches what the Simulation Object Editor (SOE) itself writes):

| File | Role | Goes to |
|---|---|---|
| `<name>.flt` | the 3D model (MAK accepts OpenFlight or FBX, not glTF) | `SharedData/ModelData/Vehicles/Surface/<name>/` |
| `<name>.ommx` | model definition: schema `Watercraft` for ships (`Entity` otherwise), `filename` only | `<sms>/gui/visuals/UserData/` |
| `<name>.leaf` | element definition: the donor's, renamed, 3D and XR model pointed at ours | `<sms>/gui/visuals/Entity/` |
| `<name>.metx` | DIS type -> element definition | `<sms>/gui/visuals/Entity/` |
| `<name>.entity` | simulation object, cloned from a donor entity | `<sms>/vrfSim/` |

## Done
- **Pipeline** (separate repo `vrf-pipeline`, local only: branch `feat/openflight-writer`, then `feat/model-kinds`
  at `0802e57`): inspect glb -> supports -> convert -> verify model -> generate -> validate, with a report.
  Standard-library Python; 109 tests.
- **Findings from the MAK manuals** (Adding Content reference, VR-Forces 5.1.1 Users Guide; cited by section):
  - FBX parts articulate only if their node names are listed in the install's `FBX_NodeNameMap.csv` (21.1.2).
  - Articulated parts: one node per part, geometry beneath it, child parts under their parent part, origin at the
    rotation axis, no rotation in the neutral pose (21.4). Part codes from Table 58 (e.g. radar 1 = 5376).
  - `.entity` objectType has 8 fields: the VR-Forces object super-type (`1` = individual, UG D.3.1) + the DIS type.
  - A new SMS keeps its own visual definitions in `<sms>/gui/visuals` (UG 64.4); the SOE's "copy existing model"
    keeps the donor's systems (UG 65.3.1).
- **OpenFlight writer, no Blender:** each moving part becomes a DOF node with an `@dis articulated_part <code>
  rotate_min p,r,y ...` comment, in the same format as MAK's stock models. MAK's own `medfTool --writeNodeInfo` loads
  the file and confirms every part, and its decrypted output shows the geometry and colours.
- **Blender exports** (`parts.json`, `spec.json`, `build_report.json`) feed a manifest draft: joints -> parts and
  motions, bow from `socket_bow`, donor suggested by size (civilian preferred). `spec.json` `meta` can be stale
  template data and is ignored; `custom_ops` code is never executed.
- **Hand import in the SOE** (Harmony of the Seas, compared file by file):
  - The pipeline's entity showed a *generic warship*: no `.leaf` existed, so the type fell back to the stock
    `1:3:-1:...` "Surface" visual. Fixed: `.leaf` generated by cloning the donor's element definition; it
    reproduces the SOE's file line for line.
  - The ship rendered *white*: MAK ignored OpenFlight material-palette colours. Fixed: colour now rides on each face.
  - Articulation worked: both radars animate.
  - Second hand import (radars added by hand, "Calculate Support Points and Bounding Volume from Displayed
    Model"): bounding volume and both radars match the pipeline's. The pipeline had kept the donor's support
    points; it now calculates them from the hull at the waterline (down 0, as on 144 of 159 stock ships). The
    editor's button put them on the keel, 9.3 m down. The donor's nav data is now cleared along with its
    object geometry.
- **Harmony of the Seas** (project `p_e4257421`): DIS type `1:3:15:80:1:0:0` (platform, surface, Bahamas,
  passenger vessel, generic cruise ship; unused in the install); radars 5376 and 5408 (azimuth); 28 joints left
  static (davits, azipods, propellers and thruster props have no fitting DIS code); donor `Super_Tanker`
  (`Cruise_Ship` is the closer match in kind).

- **Any model kind, not only ships** (vrf-pipeline `feat/model-kinds`; here `feat/mak-kinds`, cut from
  `feat/mak-export`, pushed):
  - One profile per kind in `mak/pipeline/profiles.py`: DIS kind and domain, platform file, ModelData folder,
    model schema, where the origin sits, how support points are set. Kinds: ground vehicle, fixed-wing,
    helicopter, surface ship, submarine, space object, building, static object, munition, human, animal.
  - Evidence (manual sections, no copied text): origin per domain (Adding Content 21.2.1); every stock model
    definition uses the `Entity` schema except ships and buoys (`Watercraft`) and characters
    (`DiGuyCharacter`); stock type mappings use -1 as a wildcard, so the donor's visual is found by best
    match; lifeforms are DI-Guy characters chosen in the `.entity` (Adding Content 25.2, Users Guide
    66.1.10), so a human or animal is not a model import; buildings are cultural features that can embed
    in the terrain with their own model as object geometry (Users Guide 66.1.6-66.1.8); a simulated
    munition also needs an entry in the SMS's ammunition table before a weapon can fire it (Users Guide
    66.5, 73, 74.2.2).
  - Support points now come from the geometry for everything that stands on the ground (lowest 5% of the
    model: main gear plus nose wheel on an aircraft, front corners plus rear centre on a building).
  - Gates: one full export per kind with stock donors, MAK's reader loading each model. **Only the ship is
    checked against a hand import**; every other kind reports `kind-untested`.
  - Editor: `mak.json` takes an optional `kind`; the installer merges a munition's ammunition entry into the
    custom SMS's table (with a backup). Crew are still listed as not exported.
  - Gates after the change: vrf-pipeline 109; `mak/tests` 127 (+5 skipped without the Harmony files);
    `tests/mak` passed; server 320; web typecheck and 133 tests.

- **Entity named after the project.** Harmony exported as "Container ship (200 m feeder, gearless).entity":

## Decisions
- OpenFlight is the default model format; FBX via Blender stays as an option.
- Integration (approved plan): the pipeline moves into this repo as `mak/`, alongside `unreal/`; MAK settings
  (DIS type, donor, part codes) are stored **on the ship project** without a new version; **ship only** for now
  (crew listed as not exported); the editor can **install into a named custom SMS** after confirmation, never a
  stock one, backing up anything it overwrites.
- The MAK manuals and SOE-written files stay out of this public repo (licence rule); tests rebuild from the
  installed VR-Forces instead.
